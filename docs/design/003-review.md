# 003 设计评审：数据标签增强（v0.3.2）

> 评审对象：`docs/design/003-data-grid-v0.3.2.md`
> 评审人：director
> 日期：2026-11-05
> 评审依据：`director.md` 五维标准、`panoramix-engineering/SKILL.md`、`ARCHITECTURE.md`、`ROADMAP.md`、当前代码（`frontend/src/components/DBView.vue`、`internal/db/mysql.go`、`internal/app/service.go`、`internal/app/ai.go`、`frontend/src/i18n/*`）

## 评审结论：有条件通过

方向成立，取舍基本站得住，竞品调研和交互分层是这轮设计里最扎实的部分：列可见性、结构化筛选、快捷筛选都是 TablePlus / DataGrip / DBeaver 的标配，我们不是"看起来酷"，是补齐短板；"不 COUNT、不做 DISTINCT 值列表、不做客户端过滤"的克制也对。

但有 7 处必须先改，其中 4 处是事实/数据安全层面的硬问题，不是文案问题：

1. 设计依赖"列注释参与搜索"，但当前 `DescribeTable` 根本拿不到注释（`Comment` 永远是空串）；
2. 快捷筛选在高级 WHERE 模式下完全没有定义；
3. 待提交编辑保护漏掉了"切换连接"这条真实的数据丢失路径，且多处状态是在保护前就改掉的；
4. 被保护流程复用的 `applyEdits` 仍在用字符串拼 UPDATE，反斜杠会破坏/篡改数据，且无事务；
5. Wails 错误哨兵无法原样到达前端；
6. RawWhere 校验与"结构化 → 高级"预填的语义细节需要落到可测试的词法层；
7. "筛选条件不进入 AI payload"的表述不严谨。

修完阻塞项、把保护 PR 前置后，可以进入实现。

## 评审重点逐条结论

### 1. 价值与范围

- **列可见性**：保留。宽表阅读是每天多次的高频动作，且持久化后切表恢复，ROI 最高。
- **结构化筛选**：保留。5 条上限 + 固定操作符集合 + 仅 AND，是对的范围；不要再加 OR/分组。
- **快捷筛选**：保留。它解决的是"从值出发"，和构建器不是同一路径；本轮做它是对的。
- **待提交编辑保护**：不是"顺手修"，是**阻塞项**。设计自己说对了：筛选会显著提高重新查询频率，而 `loadTableData` 现在在入口无条件清空 `pending/editing`（`DBView.vue:375-401`）。不做保护，这轮功能上线即放大既有数据丢失。同意列为"必须修"。
- **能不能再砍**：四块都必要，不建议砍功能。真正该砍的是实现风险：把保护拆成独立 PR 先落，`applyEdits` 的写入改造一并做；"在查询标签打开"和 SQL 预览成本低、信任价值高，保留。
- **排期**：保护覆盖所有重查入口 + 参数化写入 + 91 项手工验收，按当前范围 1–1.5 周不可信，按 2 周排；先交付保护，再交付筛选。

### 2. 交互决策

- **结构化与高级 WHERE 互斥**：同意互斥，不要两者同时 AND。风险不在互斥本身，而在"切换表就重置为结构化"：现有 WHERE 用户每切一次表就被迫回到构建器。建议在会话内按标签记住"上次使用的模式"（只记模式，不记文本；切表仍清空条件/WHERE），重启后回默认结构化。这样既保留唯一真相，也不惩罚老用户。
- **筛选不持久化、列可见性持久化**：不对称合理，保留。筛选决定"你看到的是不是全量"，静默恢复比列隐藏危险得多；列隐藏有"列 x/y"这个持续可见的证据。前提是：工具栏的列计数必须**始终可见**，隐藏数 > 0 时给视觉强调，否则用户仍然会问"我的列去哪了"。
- **快捷筛选"始终追加、不自动应用"**：可以接受，和"显式 Apply"的全局原则一致，但比竞品多一步（右键 → 选菜单 → 点应用）。建议面板打开后把焦点/高亮放在"应用筛选"；如果条件无草稿冲突，可考虑 `Shift + 右键` 直接应用（非阻塞）。真正阻塞的是高级模式下的行为未定义，见阻塞项 2。

### 3. 数据安全

- **隐藏列上的待提交编辑**：索引设计是对的——`visibleRefs` 只影响渲染，`pending`/`applyEdits` 继续用原始列索引（`DBView.vue:451-504`），隐藏列仍能生成 UPDATE。但"能生成"不等于"生成得对"：当前 UPDATE 是字符串拼接，见阻塞项 4。保护弹窗的"N 处位于隐藏列"计数、复合主键、隐藏主键列都要进验收。
- **CSV 只导出可见列**：方向对（与屏幕一致），但这是对既有行为的改变（当前导出全部列，`DBView.vue:638-653`），用户容易以为数据丢了。建议按钮/浮层明确写"CSV（当前页 · 可见列）"，导出后 toast "已导出 N 列，隐藏 M 列"；tooltip 同时说明导出的是数据库当前值、不含未提交修改。不要为了"全量"改回全列，那会和屏幕语义冲突。
- **快捷筛选使用数据库当前值**：决策本身可接受（避免用未落库值筛出 0 行），但只靠 toast 不够。右键菜单项应直接显示将使用的值，例如"按数据库值筛选（= O'Reilly）"，让用户在点击前就看到差异；否则"屏幕显示新值、实际按旧值筛"仍然费解。备选是先把快捷筛选纳入保护流程（先提交/丢弃再筛），但交互更重，不推荐本轮做。

### 4. 技术风险

- **列可见性持久化位置**：`localStorage` 可以接受，不需要新表，也不建议塞进现有 `settings` 表。项目已有 `panoramix.locale`、`panoramix.sqlHistory` 的本地偏好先例；列偏好是非敏感 UI 状态，走 localStorage 不必新增绑定/SQLite 迁移。代价要写清：Wails 开发态与生产态 origin 不同，偏好不互通；WebView 数据被清空时偏好静默丢失；写入失败静默忽略。连接 ID 在 SQLite 中稳定，连接改名不影响；表改名会留下孤儿 key（应用内改名时顺手清理即可）；列改名靠"隐藏集合 ∩ 当前列"处理，设计已覆盖。删除连接的前缀清理要真正落进 `askDelete`（`DBView.vue:73-84`），不能只写在文档里。
- **筛选 SQL 的转义与注入**：结构化条件是参数化的，标识符走 `quoteIdent`，LIKE 用 `!` 转义，方向正确。注入面只剩下 RawWhere，而设计已明确"这不是安全沙箱"——这是诚实的，但校验必须用**词法扫描**而不是字符串包含，且要覆盖版本注释（`/*!50000 ... */` 是可执行 SQL，见 SKILL 踩坑）。详见阻塞项 6。
- **与 AI 的边界**：数据标签不放 AI、不做双向转换、只做"在查询标签打开"的确定性桥接，边界是对的。问题只有一处表述：一旦把含内联值的 SQL 送进查询标签，用户再用 v0.3.1 的 explain/fix 发送，payload 里会包含这段 SQL（`internal/ai/payload.go` 的 `BuildInput.SQL`）。所以"筛选条件不进入 AI payload"不是绝对事实，应改成"v0.3.2 不新增任何自动发送路径；用户主动打开 SQL 并发送时，值随 SQL 进入查询标签的 payload，仍受 v0.3.1 预览约束"。

### 5. 可验证性

91 项验收本身可执行，但其中大部分只能手工做，且后端校验逻辑如果和 `DESCRIBE` 绑死，就难以单测。建议：

- **必须自动化（Go）**：builder 的纯函数层——所有操作符 × 类型矩阵、`escapeLike`、NULL/空串/引号/反斜杠/Unicode/NUL、分页边界、列/操作符/模式冲突、RawWhere 的顶层分号/注释/子句/子查询 LIMIT/版本注释/字符串内关键字、preview 与执行谓词一致。把 `validateAndBuild(cols []ColumnInfo, q TableQuery)` 与 `DESCRIBE` 分离，测试注入假列定义，不要依赖真实 MySQL。
- **必须自动化（前端）**：`gridPrefs.ts` 的 key 编码、损坏 JSON、版本不匹配、未知列求交、0 列修复。项目当前没有 vitest（`frontend/package.json`），"纯函数便于测试"目前是空话；要么在 PR1 加一个最小 vitest 配置，要么明确这部分只做手工验收并接受回归风险。建议加。
- **必须自动化（工程）**：错误码（不是英文消息字符串）稳定；`redactSQLError` 覆盖新路径；i18n 中英 key 对齐（加一个小脚本，别靠肉眼）。
- **手工必测**：所有保护入口（含切换连接）、隐藏列 pending、CSV 可见列、快捷筛选各类型、并发/旧响应丢弃、60s 超时、MySQL 8.0 真实数据。建议把数据丢失、转义/注入、隐藏列写入、CSV 语义标为发布门禁。

## 必须修改（阻塞）

### 1. 列注释数据源不存在，注释搜索/提示无法实现

`internal/db/mysql.go:404-454` 的 `DescribeTable` 只执行 `DESCRIBE`。MySQL `DESCRIBE` 返回 `Field / Type / Null / Key / Default / Extra`，**没有 Comment 列**；因此 `get("Comment")` 恒为空字符串。设计 §3.2.2 的"注释 tooltip、注释参与搜索"和验收 §7.2 的"搜索 邮箱 命中 email"在当前实现上不可能通过。

建议：`DescribeTable` 改用 `SHOW FULL COLUMNS FROM db.table`（返回 Comment）或查询 `information_schema.COLUMNS.COLUMN_COMMENT`，保持列顺序与现有 `ColumnInfo` 字段映射；把行解析抽成纯函数并加测试。若不想扩 `DescribeTable` 的职责，至少为数据标签新增一个带注释的元数据接口。验收文档同步。

### 2. 高级 WHERE 模式下的快捷筛选没有定义

§3.3.6 只说"追加到现有条件，打开筛选面板"，但高级模式下 `conditions` 为空、`RawWhere` 才是唯一真相，且两种模式互斥。当前设计会导致三种都不成立的实现：追加到空条件、静默丢弃 RawWhere、把文本拼进 RawWhere。

必须在三种方案中明确一种并写进验收：

- 推荐：高级模式下右键菜单的快捷筛选项禁用，tooltip "高级 WHERE 模式下不可用；先返回筛选器"；列头"按此列筛选…"同样处理。简单、不改变谓词、不制造第二真相。
- 或：右键后弹确认"返回筛选器会清除当前高级 WHERE"，确认后切回结构化并追加条件。
- 不建议：把条件文本拼到 RawWhere——需要字面量转义，且破坏"单一来源"，与互斥原则冲突。

同时补一条：筛选面板已打开且存在未应用草稿时，快捷筛选是追加到草稿还是丢弃草稿？建议追加到草稿并聚焦新行，不能静默丢弃用户正在编辑的条件。

### 3. 待提交编辑保护的覆盖面与执行顺序不完整

设计把触发操作列得很全，但代码里还有一条真实路径没进列表：

- `watch(activeId)` 在切换连接时执行 `tabs.value = []`、`activeTabId = ''`（`DBView.vue:1030-1042`），待提交修改直接消失。切换到 Redis 连接同理。这必须加入保护清单：拦截连接点击（不能等 watch 触发后再弹窗），或在切换前同步确认。
- `openTableStructure` / `openTableData` 先调 `ensureDataTab` 改 `tab.table`，再加载（`DBView.vue:150-160,209-244`）。保护必须在**动作入口** await，且捕获旧的 `{connId, database, table, result, pending}`；不能只写在 `ensureDataTab` 注释里，否则结构标签已切换、数据标签未切换，取消后界面处于半切换状态。
- 所有状态变更必须在保护通过后发生：当前 `nextPage` 先 `tab.page++` 再加载（`DBView.vue:519-527`），`sortTableByColumn` 先改排序再加载。若保护弹窗取消，页码/排序必须回滚或根本不改。
- 单一收口：给 `loadTableData` 加显式意图参数（例如 `loadTableData(tab, mode: 'plain' | 'discard' | 'applied')`），`pending.length > 0` 且意图不允许时直接拒绝执行；然后用 `grep loadTableData` 逐一确认所有调用点都经过保护。不要依赖"每个入口记得调 guard"。
- "应用修改并继续"的失败语义要定义到语句级：先应用、后执行原操作；应用失败则原操作不执行；如果部分 UPDATE 已成功，pending 必须裁剪或回滚（见阻塞项 4），不能保留全量让用户重复应用。
- PR 顺序调整：保护不能放在 PR4。至少与结构化筛选同 PR，最好作为独立 PR 先落（PR0/PR1），否则 PR3 本身就在制造更频繁的静默丢失。
- 验收补：切换连接、切换到 Redis、跨库/跨表、保护弹窗期间重复点击、取消后页码/排序不变。

### 4. `applyEdits` 的写入路径必须先参数化并定义部分失败

这轮把 `applyEdits` 拉进了"每次筛选/排序/翻页都可能自动调用"的路径，但它现在的实现不适合承担数据安全责任：

- `sqlLiteral` 只把 `'` 双写（`DBView.vue:451-454`），没有处理反斜杠。MySQL 默认模式下 `\` 是转义符：编辑成 `C:\new` 会被写成换行，`C:\` 会破坏引号，甚至拼接出额外 SQL。`NO_BACKSLASH_ESCAPES` 下语义又相反。
- 每条 UPDATE 单独 `DBQuery`，没有事务。中途失败时前面的行已写入，`pending` 仍保留全部，用户重试会得到"部分成功 + 重复错误"的混合状态。
- 主键值同样走 `sqlLiteral`，同一个问题也影响 WHERE。

建议：新增参数化写入绑定（例如 `DBApplyEdits` 或通用 `DBExec(connID, sql, args)`），由 Go 侧用 `?` 生成 `SET`/`WHERE`，整批放入事务；返回每条结果，失败时回滚（或明确裁剪已成功项并提示"已应用 X/Y"）。至少必须先做到参数化，不再拼字符串。补测试：反斜杠、单引号、NUL、emoji、复合主键、bigint 主键、第二条 UPDATE 失败。

这是既有问题，但本轮的保护流程会把它变成自动化主路径，不能带着它上线。

### 5. 错误哨兵跨 Wails 边界到不了前端

`ErrFilterModeConflict` 等 Go sentinel 在 Wails 绑定里会变成 `error.Error()` 字符串，前端拿不到 `errors.Is` 的身份。设计 §4.4 的"错误哨兵（供前端本地化）"若按英文消息匹配，会随文案改动而碎。

建议沿用项目已有的 `code: message` 约定（`internal/app/ai.go:721-741`，前端 `AIPanel.vue:414` 解析 code）：返回 `filter_mode_conflict: ...`、`too_many_conditions: ...`、`unknown_column: ...`、`operator_not_allowed: ...`、`unsafe_raw_where: ...`、`invalid_page: ...`，前端按 code 映射 i18n，message 只做兜底展示。或者让 `DBTableData` 返回带 `errorCode` 的结构体。两种都可以，但必须稳定、可测试。

同时：两个新绑定失败时的日志必须走 `redactSQLError`，且只记录 `table/条件数/模式/耗时/错误码`，不记录值、RawWhere、结果行（`service.go:900-914` 已有先例）。

### 6. RawWhere 校验与"结构化 → 高级"预填的语义要落到词法层

- **复用词法器**：`scanTopKeywords` 已能跳过字符串、反引号、注释、括号内内容（`mysql.go:133-261`）。顶层分号/注释/`ORDER BY`/`UNION` 判定应基于它，不能用 `strings.Contains`。必须覆盖：字符串里的 `;` 和 `--`、反引号标识符、子查询里的 `LIMIT` 允许、顶层 `UNION` 拒绝、`/*!50000 ... */` 版本注释（可执行，必须拒绝）、列名恰好叫 `order`/`group` 时不能误杀"ORDER BY / GROUP BY"短语。
- **前导 WHERE**：现有占位符是"筛选条件（WHERE 片段），如 status = 1"（`i18n/zh-CN.ts:128`），但老用户很可能输入 `WHERE status = 1`。设计没有定义。建议在 RawWhere 校验时拒绝并给明确提示，或在最前面自动去掉一个 `WHERE`（只去一次），并加测试。否则生成 `WHERE WHERE ...`。
- **预填语义**：结构化 → 高级时，设计把后端返回的 WHERE 作为**已应用**谓词，然后走 RawWhere 执行。但预填是把参数化条件内联成字面量；若会话启用了 `NO_BACKSLASH_ESCAPES`，含反斜杠的值在两种路径下语义不同。建议：内部仍保留条件数组作为 Applied，高级输入框只做展示/编辑；用户真正修改并应用后才切换到 RawWhere。至少要在文档里明确这个风险和测试。
- **每次请求都 DESCRIBE**：设计要求 `DBTableData` 先用 `DESCRIBE` 拿列再校验。分页/排序也会多一次往返。建议按 `(connId, database, table)` 缓存元数据并显式失效（DDL 后、未知列错误时），同时把 `validateAndBuild(cols, q)` 做成纯函数以便单测。
- **预览页码**：面板预览用当前 `page`，但应用筛选会把页码重置到 0；预览与执行 SQL 的 OFFSET 可能不同。预览草稿时固定 page=0，或明确标注"应用后回到第 1 页"。

### 7. AI 边界表述需要修正（文档问题，工作量小）

§2.3/§4.6/§7.8 的"筛选条件不进入 AI payload"过于绝对。真实情况是：v0.3.2 不新增任何自动 AI 路径；但"在查询标签打开"会把含内联值的完整 SQL 放进编辑器，用户随后用 v0.3.1 的 explain/fix 发送时，这段 SQL（含值）会进入 payload——这是用户主动行为，且受 v0.3.1 预览约束。请改成这个表述，并在验收里补一条："打开 SQL 不自动触发 AI；用户发送时预览可见 SQL 文本"。否则一旦有人用云端 provider，文档会站不住。

## 建议改进（不阻塞）

- 列可见性：在 `askDelete` 中按前缀清理 localStorage；应用内表改名时清理旧 key；`gridPrefs` 集中读写，不要在 DBView 里散落 `localStorage.getItem`。若未来要求"换机器/重装仍保留"，再迁到 `settings` 表并加绑定，本轮不必。
- 模式记忆：按连接/标签在会话内记住 structured/raw（不持久化），切表只清条件与文本，不强制回结构化；对现有 WHERE 用户更友好。
- CSV：按钮文案改为"CSV（可见列）"或导出后 toast 隐藏列数；tooltip 同时说明"当前页、数据库值、不含未提交修改"。
- 快捷筛选：有 pending 的单元格，菜单项直接展示数据库值；"包含此值"在值含 `%`/`_`/`!` 时也走同一 `escapeLike` 路径，避免两套转义。
- "查看 SQL"有两个含义（面板草稿预览 vs 结果元信息已执行 SQL）。建议分别叫"预览 SQL"和"查看已执行 SQL"，减少误解。
- 列元数据加载失败时，列面板其实只依赖 `result.columns` 的列名，可以继续可用；只有筛选操作符/类型依赖 `DESCRIBE`。不要一起禁用。
- DDL 与 pending：结构标签执行 ALTER 前，若同表数据标签有 pending，先提示；列被删除/改类型后，明确"失效 pending 如何处理"，不要只标记 stale。否则用户点应用必失败。
- 外部 DDL 导致 `unknown_column`：应用失败后自动刷新一次元数据并移除失效条件，而不是让用户反复点。
- `loadSeq`：旧响应不仅要丢弃数据，也不能把 `loading` 置 false 或清掉新请求的错误；建议所有状态更新都带 seq 判断。快速点多个 chip × 会并发打 5 条长查询（连接池 5），建议 loading 中禁用 chip × 或做单飞。
- "应用修改并继续"后原查询失败：此时修改已提交但网格仍是旧值，必须标注"修改已应用；查询失败，显示的是上一次结果"，并提供刷新，避免用户以为修改没生效。
- `DataTabState` 补 `columnsStale`、`filterError` 来源；切表重置清单要覆盖 `conditionsDraft/rawWhereDraft/rawPrefill/conditionsSnapshot/filterPanelOpen/columnsPanelOpen/lastTableSQL/filterError/hiddenColumns/columnsStale`。
- 窄窗口：正文写 <900px，验收写 960px，统一一个值。
- 分页边界：`Page <= 1_000_000 × PageSize 5000` 与 offset 上限 1e9 不一致，明确是先算 offset 再校验，还是收紧 page 上限。
- 丢弃编辑的 ✕ 是显式操作，但和 ✓ 相邻，建议 pending 数较多时二次确认（可选）。
- 工程：加 vitest（哪怕只跑 `gridPrefs` 和数字正则）；加 i18n 中英 key 对齐脚本；`ARCHITECTURE.md` 补 `internal/db/table_query.go`、两个绑定、localStorage 偏好与"无新事件"。

## 风险提示

- **数据丢失面仍可能漏口**：保护是横切改动，`DBView.vue` 已 2477 行，入口包括树点击、刷新、排序、翻页、页大小、筛选应用、chip 删除、清除、结构标签切换、连接切换、Redis 切换。漏一个就是一次静默丢失。`watch(activeId)` 已经是现成反例，必须用"单一收口 + 全量调用点清单"而不是逐处补丁。
- **写入风险**：即使保护交互完美，`applyEdits` 的字符串拼接仍可能在含反斜杠/特殊字符时写坏数据；无事务时部分成功会制造最难解释的状态。这两点必须在本轮解决，否则"保护数据"的口号会被写入路径打脸。
- **并发与超时**：没有取消能力，`loadSeq` 只隐藏旧结果，旧查询仍在数据库上跑；5 个连接池可能被快速操作占满。60s 超时对无索引大表是常态，错误文案要有"加索引/缩小条件"的具体建议，不要只显示 MySQL 原文。
- **隐藏列不等于省流量**：`SELECT *` 仍会把 BLOB/JSON 全量取回 WebView。用户可能期待"隐藏大字段变快"，实际不会；文档已写明，但产品文案不要暗示性能提升。
- **元数据过期**：应用外 DDL（另一个客户端改列）不会触发 `columnsStale`，会出现条件持续失败。建议对 `unknown_column` 做一次自动刷新 + 条件清理。
- **localStorage 偏好丢失**：WebView 数据清理、origin 变化（dev/prod）、隐私模式都会让列偏好消失；写了失败也静默。属于可接受降级，但不要把"列视图记忆"当强承诺。
- **排期**：保护（含参数化写入与事务）+ builder + 3 个新组件 + 20+ i18n key + 91 项验收，1–1.5 周不现实。按 2 周排，并把保护单独作为第一个可验收增量；如果时间紧，先砍"在查询标签打开"或列面板的搜索/全选，不要砍保护。
- **回归面**：数据标签的编辑、排序、CSV、分页都在同一文件里改；列可见性改变的是渲染索引，最容易出现"编辑错列/筛选错列/CSV 错列"。PR 验收必须带一组"隐藏列 + 排序 + 编辑 + CSV"的组合回归，而不只是单点。

## 一句话结论

方向对、取舍基本站得住；但"列注释根本拿不到"是事实前提错误，高级模式下快捷筛选、连接切换时的待提交保护、拼接式 UPDATE 和三处语义细节必须先修，且保护要前移到筛选 PR 之前——把这些改完再进入实现。
